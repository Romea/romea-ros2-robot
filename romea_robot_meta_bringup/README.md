# romea_robot_meta_bringup

## 1) Overview

`romea_robot_meta_bringup` provides tools to assemble and launch a complete robot system from several device meta-descriptions.

It is built on top of the ROMEA meta-description workflow and acts as a high-level orchestrator for:

* a mobile base
* a joystick or teleoperation input device
* sensors such as lidar, GPS, IMU and cameras
* implements attached to the robot
* manipulators such as robotic arms

The package does not describe each device directly. Instead, it references the meta-description file of each component and delegates generation and launch to the corresponding `<device_type>_meta_bringup` package.

It can generate consistent ROS2 artifacts for the full robot:

* configuration files -> merge the mobile base and device configurations
* launch files -> include the launch files generated by each component package
* URDF description files -> combine the mobile base reference URDF and the device URDF fragments

---

## 2) Robot meta-description and components

A `robot meta-description` is a YAML file that describes the composition of a complete robot.

It centralizes:

* the mobile base meta-description
* the joystick meta-description used by teleoperation stacks
* optional device meta-descriptions
* the type of each optional device so the matching meta-bringup package can be selected

The robot meta-description is intentionally small. All detailed hardware, geometry, launch and record information remains in the component meta-description files.

---

### Format

```yaml
base:
  meta_description: path/to/mobile_base_meta_description.yaml

joystick:
  meta_description: path/to/joystick_meta_description.yaml

devices:
  - type: lidar
    meta_description: path/to/lidar_meta_description.yaml
  - type: gps
    meta_description: path/to/gps_meta_description.yaml
  - type: imu
    meta_description: path/to/imu_meta_description.yaml
  - type: implement
    meta_description: path/to/implement_meta_description.yaml
  - type: arm
    meta_description: path/to/arm_meta_description.yaml
```

`base` and `joystick` are mandatory.

The `type` field of each entry in `devices` is used to load the matching package:

```text
romea_<type>_meta_bringup
```

Each referenced file follows the format of the package that handles the corresponding component:

| Entry | Package |
|:------|:--------|
| `base` | `romea_mobile_base_meta_bringup` |
| `joystick` | `romea_joystick_meta_bringup` |
| `type: lidar` | `romea_lidar_meta_bringup` |
| `type: gps` | `romea_gps_meta_bringup` |
| `type: imu` | `romea_imu_meta_bringup` |
| `type: camera` | `romea_camera_meta_bringup` |
| `type: implement` | `romea_implement_meta_bringup` |
| `type: arm` | `romea_arm_meta_bringup` |

### Component responsibilities

At robot level, `romea_robot_meta_bringup` only resolves the composition and delegates each component to its own meta-bringup package.

| Component | Responsibility |
|:----------|:---------------|
| `base` | select the concrete robot model, then generate the robot base configuration, reference URDF, ros2_control description and launch files that start the mobile base controller, robot-integrated actuator controllers such as front or rear three-point hitches, and teleoperation |
| `joystick` | provide the joystick driver launch and joystick mapping used by teleoperation |
| sensors | generate sensor configuration, URDF fragments, driver launches and simulation bridge launches |
| implements | generate implement configuration, URDF fragments and launch files for tools attached to the robot, including communication or control nodes when the implement is active or intelligent, and simulation bridge launches |
| manipulators | generate manipulator configuration, URDF fragments, ros2_control description, driver launches and simulation bridge launches |

The robot meta-description therefore stays independent from the details of each device. It only describes which components are present and where their meta-description files are located.

## 3) Scripts

`romea_robot_meta_bringup` provides scripts to generate full-robot artifacts from a robot meta-description.

The scripts use the historical `name:value` syntax.

### Generate configuration file

```bash
ros2 run romea_robot_meta_bringup generate_configuration_file.py \
  meta_description_file_path:path/to/robot_meta_description.yaml \
  extended:false
```

This command generates a merged YAML configuration file.

The output contains one top-level key per generated component. The joystick is not included in this merged configuration because it is used mainly to configure the mobile base teleoperation launch.

Example output, simplified:

```yaml
base:
  model: adap2e
  version: one
  manufacturer: inrae
  type: 1FAS4WD

lidar:
  model: lms
  version: "151"
  manufacturer: sick
  rate: 50

gps:
  model: asterx
  manufacturer: septentrio
  rate: 10

cultivator:
  model: cultivator
  version: mounted
```

---

### Generate URDF description

```bash
ros2 run romea_robot_meta_bringup generate_urdf_description.py \
  mode:simulation_gazebo \
  robot_namespace:robot \
  meta_description_file_path:path/to/robot_meta_description.yaml
```

This command generates a complete robot URDF by:

* generating the mobile base reference URDF first
* appending the URDF fragments of every device listed in `devices`

The generated URDF can include sensors, implements and manipulators attached to the robot according to each component `location` section.

Example output, simplified:

```xml
<robot name="robot">
  <link name="robot_base_link">
    ...
  </link>

  <link name="robot_lidar_link">
    ...
  </link>

  <joint name="robot_lidar_joint" type="fixed">
    <parent link="robot_base_link"/>
    <child link="robot_lidar_link"/>
    ...
  </joint>

  <link name="robot_gps_link">
    ...
  </link>

  <link name="robot_cultivator_link">
    ...
  </link>
</robot>
```

---

### Generate launch file

```bash
ros2 run romea_robot_meta_bringup generate_launch_file.py \
  robot_namespace:robot \
  meta_description_file_path:path/to/robot_meta_description.yaml
```

This command generates a YAML launch file that includes:

* the joystick launch file
* the mobile base launch file
* the launch file of each device listed in `devices`

Example output, simplified:

```yaml
launch:
- arg:
    name: mode
    default: live
- include:
    file: $(find-pkg-share romea_joystick_meta_bringup)/launch/joystick.launch.py
    arg:
    - {name: mode, value: $(var mode)}
    - {name: robot_namespace, value: robot}
    - {name: meta_description_file_path, value: config/joystick.yaml}
- include:
    file: $(find-pkg-share romea_mobile_base_meta_bringup)/launch/mobile_base.launch.py
    arg:
    - {name: mode, value: $(var mode)}
    - {name: robot_namespace, value: robot}
    - {name: mobile_base_meta_description_file_path, value: config/base.yaml}
    - {name: joystick_meta_description_file_path, value: config/joystick.yaml}
- include:
    file: $(find-pkg-share romea_lidar_meta_bringup)/launch/lidar.launch.py
    arg:
    - {name: mode, value: $(var mode)}
    - {name: robot_namespace, value: robot}
    - {name: meta_description_file_path, value: config/lidar_front.yaml}
```

## 4) Usage

The package provides three launch files:

* `robot.launch.py` -> starts the robot components from a robot meta-description
* `robot_state_publisher.launch.py` -> publishes the full robot description and joint states
* `simulation_test.launch.py` -> starts a simulator, spawns the robot entity and starts robot components

### Dynamic bringup

```bash
ros2 launch romea_robot_meta_bringup robot.launch.py \
  mode:=live \
  robot_namespace:=robot \
  meta_description_file_path:=path/to/robot_meta_description.yaml
```

When using `robot.launch.py`, the following steps are performed automatically:

* load the robot meta-description
* generate the full robot launch file in `/tmp` directory
* include the generated launch file
* forward the selected `mode` to all component launches

The `mode` parameter controls the behavior of component launch files:

* `live` -> starts real drivers and controllers when selected by each component
* `simulation_<simulator>` -> starts simulation bridges and simulation-specific nodes when selected by each component

---

### Robot state publisher

```bash
ros2 launch romea_robot_meta_bringup robot_state_publisher.launch.py \
  mode:=live \
  robot_namespace:=robot \
  meta_description_file_path:=path/to/robot_meta_description.yaml
```

This launch file:

* generates the complete robot URDF
* starts `joint_state_publisher`
* starts `robot_state_publisher`
* pushes both nodes into the robot namespace

The `joint_state_publisher` node republishes a robot-level `joint_states` topic by aggregating the mobile base joint states from `<base_name>/joint_states` and, when present, the joint states of each arm from `<arm_name>/joint_states`.

---

### Simulation test

```bash
ros2 launch romea_robot_meta_bringup simulation_test.launch.py \
  simulator_type:=gazebo \
  robot_namespace:=robot \
  meta_description_file_path:=path/to/robot_meta_description.yaml
```

This launch file:

* starts the simulator through `romea_simulation_meta_bringup`
* generates and loads the robot entity
* calls `robot.launch.py` with `mode:=simulation_<simulator_type>`

For GPS-based localization, it also accepts `wgs84_anchor_file_path` and forwards it to the simulator launch.

## 5) Extending the robot composition

To add a new component type to a robot meta-description, the corresponding package must follow the `romea_<type>_meta_bringup` convention and provide the standard meta-bringup API:

* `load_meta_description(meta_description_file_path, robot_name=None)`
* `generate_yaml_configuration_file_str(meta_description, extended)`
* `generate_yaml_launch_file_str(meta_description)`
* `generate_xml_urdf_description_str(mode, meta_description)`

Once this package is available, the component can be added to the robot with:

```yaml
devices:
  - type: <type>
    meta_description: path/to/<type>_meta_description.yaml
```

This keeps the robot-level description independent from the details of sensors, robot-specific bases, implements and manipulators.
